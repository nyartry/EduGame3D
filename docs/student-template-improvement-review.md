# 学生配布用ひな型の改善価値と実施単位

調査日: 2026-09-11。対象: `8275e850d89d344e6ff99b18fe812dc12b15d052`。
実装前の作業ツリーに変更なし。[引き継ぎ資料](student-template-core-handoff.md)の提案を現行コードと照合した。

## 判断

改善を実施する価値はある。ただし、優先すべきなのは学生が独自機能を作り、問題を調べ、他のPCで動く作品を提出できる土台である。全提案を実装することや、ひな型の機能数を増やすことを目標にしない。

提供されたFrameworkと、学生が実装した部分・技術的な工夫を説明できることも重要になる。既存のFramework／Game分離を維持し、利用例と変更箇所の案内を各機能に添える。以下の価値・費用はコード調査からの判断であり、採用結果への効果を測定したものではない。

## 採用作品の提出要件との関係

公式の募集要項に、実行物と本人の担当箇所の説明を重視する具体例がある。

- [サイバーコネクトツー・新卒プログラマー](https://www.cc2.co.jp/recruit/?p=3293)は、オリジナル作品、実行ファイル、ソース、動画、指定readmeを求めている。[指定書式](https://www.cc2.co.jp/recruit/wp-content/uploads/2014/08/readme.txt)では、開発環境、注目してほしいプログラム、参考ソース、担当箇所、他者製コードと生成AIの利用箇所を説明する。
- [プラチナゲームズ・新卒プログラマー](https://www.platinumgames.co.jp/recruitment-information/link-new-recruit.html)は、作品説明・担当箇所・実行環境・紹介動画を求め、選考側ではビルドしないとしている。同ページの本文は公式URLの検索インデックスで確認した。

このため、R4の配布物、制作・起動手順、提供コードと学生の変更の区別には提出実務上の根拠がある。各社の要件は変更され得るため、応募時に確認する。すべての企業に共通する条件とは扱わない。

## 項目ごとの評価

| 項目 | 判断 | 現行コードの根拠と最初の実施範囲 |
| --- | --- | --- |
| R1 初期ロード失敗 | 最初に実施。小さく効果が明確 | `Win32Application::Run`が初期`LoadScene`のfalseを無視する。既存の原因情報を表示し、ループ開始前に終了する。通常遷移の復旧は維持する。 |
| R2 終了順・GPU寿命 | 高。R1の次の候補 | 正常終了のみGPU待機し、例外時はScene/UI等がrendererより先に破棄される。記録中フレームを中断し、送信済み処理を安全に終える終了契約が必要。単にデストラクタへ`WaitForGpu`を足さない。エディターも対象を確認する。 |
| R3 リサイズ | 高。独立した変更単位 | 可変サイズのウィンドウに`WM_SIZE`処理がない。描画・カメラ・UI・入力の寸法を揃える。0寸法、準備中シーン、復帰も含める。 |
| R4 配布・起動 | 高。大きな機能追加より先に整える | GameAppのPostBuildはAssimp DLLのみ。エディターのシェーダーコピーと上位フォルダー探索が不足を隠す。GameApp単独で資源を収集し、ソース外・別作業ディレクトリで確認する。 |
| R5 診断 | 高。学生配布前に必要 | 共通sinkはデバッガ出力のみで、音声・モデルに独自出力が残る。ファイルログ、操作・パス・原因の統一、必須／任意サービスの失敗方針を整える。 |
| C1 Actor管理 | 高。最初の大きなコア拡張候補 | `GameScene`のprivateな所有vectorと直接走査、非所有ポインター、手動衝突解除に生成・削除が依存する。追加／削除予約、世代付きHandle、解除・GPU寿命を小さくまとめる。現行の固定Actorサンプルの不具合を再現したわけではない。 |
| C2 Transform階層 | 有用。費用は中〜高 | `Transform`は単体SRT。部品・親子物体に有用だが、親削除、循環、せん断、再親子化の契約が必要。Coreの値型を維持してScene側へ追加する。 |
| C3 3D問い合わせ | 高。形状・段階を絞る | `ICollisionQuery`は床・境界中心。球/AABBのRaycast・Overlapから始める。Trigger通知、Sweep、カプセルを同じコミットへ含めない。 |
| C4 入力 | 高。既存の分離を活用 | `GameActions`による作品固有名の分離は既にある。価値は任意割当・複数バインド・軸・デバイス対応の追加にある。固定更新の入力保持を守る。 |
| C5 シーン・時間 | 中。利用例が必要になった段階 | Additiveは全シーン更新・末尾カメラで、個別除去や下層停止に不足する。操作要求と停止方針から分け、時間倍率等を一括追加しない。 |
| C6 クロスフェード | 中。後回し | 単一クリップの再生状態からの変更に、ルート変位・イベント・途中再要求の契約が伴う。既存再生の回帰負担が大きい。 |
| C7 ライト設定 | 小さく始めれば費用対効果が高い | 静的／スキンHLSLの照明値が固定。方向光と環境光をGameから設定する範囲なら、学生が変更効果を確認しやすい。C5/C6より先に実施してもよい。 |

C1→C2→C3→C4を絶対的な依存順にはしない。C3の形状問い合わせやC4の割当テーブルはC2がなくても進められる。ECS化、本格的な剛体物理、大型エディター、未計測の最適化は現時点では延期する。

READMEはビルド・操作説明が中心で、最小の`IScene`から学生の作品へ進む一連の案内は不足している。新規シーンの登録、Actor追加、素材差替え、提供部分と自作部分の説明を小さな教材として整える価値がある。これは新しい大型機能の実装を待つ必要がない。

## 今回の変更単位

R1だけを実装・検証し、コミット可能な状態で区切る。コミット操作はユーザーが行う。R2以降の実装を同時に進めない。

期待する挙動は、初期ロード失敗でシーン名・段階・原因を表示し、終了コード1を返すこと。SceneManagerが記録した診断を重複して出力しない。起動に成功した場合と、起動後のシーン切替失敗時の旧シーン保持・再試行を維持する。

検証結果と残る制限は[引き継ぎ後の記録](student-template-core-handoff.md#11-引き継ぎ後の記録欄)へ追記する。
